**Product:** PC Usage Intelligence

**Last updated:** 2026-09-02

# 1. Purpose

This document defines how PC Usage Intelligence synchronizes a user's local usage history between Windows devices using the user's Google Drive account as encrypted storage.

The central design constraint is:

```text
Local SQLite = source of truth
Google Drive = encrypted replication/storage layer
```

The sync system must never become a prerequisite for tracking, analytics, timeline rendering, classification, or normal application operation.

The user's data is encrypted before it leaves the device according to Document 10. Google Drive stores ciphertext and synchronization metadata required for replication, but it is not trusted with plaintext usage history.

This document specifies:

- Sync scope.
- Object model.
- Encrypted payload format.
- Upload/download workflow.
- Local sync queue.
- Idempotency.
- Conflict resolution.
- Concurrent-device behavior.
- Device enrollment and removal.
- Migration.
- Deletion/tombstones.
- Retention interactions.
- Offline operation.
- Drive failure/recovery.
- Authentication boundaries.
- Integrity checks.
- Versioning.
- Resource budgets.
- Acceptance criteria.

Cryptographic primitives and key-management mechanisms are defined in Document 10.

# 3. Core Invariants

1. Local SQLite remains the authoritative source of truth.
2. Tracking must continue when offline.
3. Sync must never block the tracker.
4. Google Drive must never receive plaintext usage history.
5. Google authentication and usage-data encryption keys remain separate.
6. Sync is opt-in independently of Google sign-in.
7. A sync failure must not reduce tracking accuracy.
8. Uploads must be retryable and idempotent.
9. Downloads must be validated before affecting local state.
10. Conflicts must never silently overwrite newer user data.
11. Deletions must propagate and must not be undone by stale replicas.
12. Private/incognito data excluded locally must never appear in a sync object.
13. Device identity must remain distinct from application/account identity.
14. A corrupted or tampered remote object must be rejected without damaging the local source of truth.
15. The user must be able to disable sync without losing local data.
16. Disconnecting sync must stop future synchronization while preserving local history unless the user separately requests deletion.
17. Sync protocol versions must be explicit and migratable.
18. The sync worker must have bounded resource usage.
19. No product behavioral telemetry is generated by the sync subsystem.
20. Remote data is not considered trusted merely because it exists in the user's Drive.

# 4. Terminology

### Device

A Windows installation participating in a user's encrypted history.

### Sync identity

Stable logical identity for a synchronized dataset/user space.

### Device identity

Stable cryptographic identity for one enrolled installation.

### Dataset

The logical synchronized usage-history namespace.

### Generation

A monotonically ordered logical state version of a dataset or collection.

### Sync object

An immutable or content-addressed encrypted object stored in Google Drive.

### Manifest

An encrypted, authenticated index describing the current logical dataset state and available objects.

### Tombstone

An authenticated record that states that an object, entity, or logical range was intentionally deleted and must not be resurrected by an older replica.

### Checkpoint

A local marker identifying the last remote state known to have been safely incorporated.

### Outbox

The local queue of pending encrypted sync mutations.

# 5. Sync Scope

The synchronized dataset is derived from the same logical model defined in Document 07.

Potentially synchronized categories:

- Application identity.
- Process/application identity mappings necessary to reconstruct history.
- Window/application usage intervals.
- Browser domain history.
- Browser page-title history when enabled and present.
- Category definitions.
- User classification rules.
- Productivity/leisure classifications.
- Relevant configuration needed to reconstruct analytics.
- Device provenance.
- Data-retention metadata.
- Deletion tombstones.
- Algorithm/schema versions where required for interpretation.

Excluded from the usage sync dataset:

- OAuth credentials.
- Access tokens.
- Refresh tokens.
- Encryption private keys.
- Windows credential material.
- Diagnostic logs unless the user explicitly exports them separately.
- Product telemetry.
- Secrets unrelated to user usage history.
- Private/incognito domain/title data.

The exact field inventory must remain consistent with Document 09.

# 8. Google Drive Role

Google Drive is used as a user-owned storage destination rather than as a general-purpose backend.

The application should create a dedicated application-specific folder/namespace within the user's Drive with least-privilege access appropriate to the chosen OAuth scope.

The application must not scan unrelated user Drive files.

The sync worker should know only the identifiers of objects belonging to the PC Usage Intelligence dataset.

The product must not treat arbitrary Drive contents as trusted sync input.

---

# 9. Authentication Boundary

Authentication answers:

```text
Who is this Google account?
```

Encryption answers:

```text
Who can decrypt this usage history?
```

These are separate.

A successful Google OAuth flow does not itself reveal the usage-data encryption key hierarchy.

The sync worker may use OAuth access/refresh credentials to call Drive, but those credentials must never become part of the encrypted usage dataset.

Token storage remains governed by Document 10.

---

# 10. Dataset Identity

The synchronized history should have a stable logical dataset identifier.

Example conceptual structure:

```text
DatasetId
 ├── Device A
 ├── Device B
 └── Device C
```

A device must not create an entirely independent history merely because its hardware or Windows installation changes.

The dataset identity is distinct from:

- Google account ID.
- Windows user SID.
- Device identity.
- SQLite database path.

---

# 11. Device Enrollment

A newly installed device follows this sequence:

```text
Install
  ↓
Create local identity
  ↓
User signs in to Google
  ↓
User explicitly enables sync
  ↓
Recover/import encrypted dataset metadata
  ↓
Establish device membership
  ↓
Merge approved local history
  ↓
Continue tracking
```

The device should not begin uploading local usage automatically merely because sync credentials are available.

Device enrollment metadata should include:

- Device ID.
- Cryptographic public identity where applicable.
- Dataset ID.
- Protocol version.
- Creation/enrollment timestamp.
- Last known synchronization generation.
- Revocation status.

No sensitive usage details are required in plaintext metadata.

---

# 12. Device Revocation

A user should be able to remove a device from synchronization.

Revocation means:

```text
Device can no longer publish to the dataset.
Device should no longer trust future dataset updates as a member.
```

Revocation must not delete that device's already-recorded local history unless the user separately chooses deletion.

The exact cryptographic revocation mechanism is defined by Document 10.

---

# 13. Sync Object Model

The protocol should avoid treating the entire SQLite database as one monolithic blob.

Recommended logical object families:

```text
Manifest
Metadata snapshot
Usage shard
Classification shard
Browser shard
Tombstone shard
Schema/protocol metadata
```

A “shard” is a bounded logical subset of data suitable for independent upload/download.

Recommended partitioning dimension:

```text
Dataset
  → month or bounded time range
      → data family
```

Example:

```text
2026-08
  applications
  browser
  classifications
  intervals
```

Exact granularity must be benchmarked against Drive object limits, sync frequency, and local CPU/storage costs.

---

# 14. Why Sharding Is Required

A monolithic database upload would create undesirable behavior:

- Tiny changes cause large uploads.
- Conflicts become coarse.
- Deletion is difficult to reason about.
- Partial recovery is poor.
- One corrupted object can block the entire history.

Sharding allows:

```text
small logical change
→ small encrypted object
→ targeted retry
→ targeted reconciliation
```

---

# 15. Object Immutability

Preferred model:

```text
Upload new object
→ publish new manifest
→ never mutate historical encrypted object in place
```

Immutable objects make retries and verification simpler.

The manifest acts as the logical pointer to the current dataset state.

Old objects can later become reclaimable only after retention/garbage-collection rules establish that no supported device or recovery process requires them.

---

# 16. Encrypted Object Envelope

Every synchronized usage object must have a versioned authenticated envelope.

Conceptual format:

```text
Magic
ProtocolVersion
ObjectType
DatasetId
ObjectId
LogicalGeneration
ProducerDeviceId
CreatedAt
PlaintextLength
Ciphertext
AuthenticationTag
```

Authenticated associated data should bind security-critical metadata such as:

- Protocol version.
- Dataset/object identity.
- Object type.
- Generation.
- Dataset/key epoch.

Sensitive fields must remain inside ciphertext where possible.

The concrete binary format and key derivation are defined in Document 10.

---

# 17. Manifest

The manifest is the authoritative encrypted index of the remote logical dataset state.

Conceptually:

```text
Manifest
 ├── dataset metadata
 ├── protocol version
 ├── key epoch
 ├── generation
 ├── device membership
 ├── object references
 ├── tombstone references
 └── consistency metadata
```

The manifest MUST be authenticated.

A manifest update should itself be represented as an immutable versioned object.

---

# 18. Manifest Visibility

Because the user should not disclose unnecessary information to the storage provider, the manifest should minimize plaintext metadata.

A practical baseline is:

```text
Drive-visible:
randomized application-specific object IDs
opaque sizes/timestamps needed by Drive

Encrypted:
dataset structure
usage dates
application names
browser/domain names
device names
classification data
```

Even object sizes and modification timing can reveal some metadata. Perfect traffic analysis resistance is out of scope for V1.

---

# 19. Change Detection

The sync planner must determine what local data requires replication.

Preferred approach:

```text
Local committed mutation
      ↓
Durable sync marker/outbox entry
      ↓
Encrypted object generation
      ↓
Upload
      ↓
Remote acknowledgement
      ↓
Mark synced
```

The tracker should not need to know whether a sync object was uploaded successfully.

---

# 20. Outbox

The local sync outbox must be durable.

Minimum fields:

- Outbox ID.
- Dataset ID.
- Object ID.
- Mutation type.
- Local generation.
- Encryption key epoch.
- Attempt count.
- Next retry time.
- Last failure code.
- State.
- Created timestamp.
- Completed timestamp.

Possible states:

```text
Pending
Encrypting
Ready
Uploading
Uploaded
AwaitingManifest
Committed
Retrying
Blocked
DeadLetter
```

A crash must not lose knowledge that an upload was pending.

---

# 21. Idempotency

Uploads may be interrupted after Drive accepts data but before the local process records success.

Therefore every object needs deterministic logical identity or an equivalent idempotency mechanism.

Retry behavior:

```text
Same logical object
→ same object identity
→ re-check remote state
→ avoid duplicate logical mutation
```

Idempotency must be tested under forced process termination.

---

# 22. Retry Policy

Sync failures are expected.

Recommended strategy:

```text
Immediate retry: very limited
Then exponential backoff
With randomized jitter
With bounded maximum interval
```

Retry classification:

```text
Transient network → retry
Rate limit → retry according to server guidance
OAuth expired → refresh/re-authenticate
Permission denied → pause and surface action
Malformed object → reject / quarantine
Corrupt local state → pause and surface repair
```

Retry storms are prohibited.

---

# 23. Pull/Reconciliation Cycle

Synchronization is bidirectional conceptually:

```text
Local changes → remote
Remote changes → local
```

A reconciliation pass should:

1. Authenticate.
2. Locate the application-specific Drive namespace.
3. Read the current remote manifest/version candidates.
4. Validate candidate manifests.
5. Compare remote generation/object references to the local checkpoint.
6. Download required objects.
7. Verify authentication/integrity.
8. Stage imported data.
9. Resolve conflicts.
10. Commit local changes transactionally.
11. Update the local sync checkpoint.
12. Publish local pending changes if necessary.
13. Garbage-collect completed queue entries.

The order may be optimized, but local data must never be partially replaced by an unverified remote state.

---

# 24. Staging Remote Data

Downloaded objects must first enter a staging area.

```text
Drive object
   ↓
Parse envelope
   ↓
Authenticate
   ↓
Decrypt
   ↓
Validate schema
   ↓
Validate IDs/ranges
   ↓
Stage
   ↓
Transactional merge
```

Never decrypt and directly overwrite production SQLite rows without validation.

---

# 25. Conflict Model

The product has several classes of state with different conflict semantics.

## 25.1 Append-oriented observations

Usage observations/events are naturally append-oriented.

Preferred rule:

```text
Union after deduplication
```

A device-local event should not disappear because another device wrote different events.

## 25.2 User edits

Examples:

- Category reassignment.
- Productivity/leisure classification.
- User identity override.
- Retention preference.

These require versioned mutations rather than blind last-write-wins.

## 25.3 Configuration

For some settings, last-write-wins may be acceptable if accompanied by deterministic ordering and visible conflict resolution.

Privacy/security settings should use explicit precedence rules and may require user confirmation rather than automatic merging.

---

# 26. Event Identity and Deduplication

Every synchronized event/entity mutation must have a stable globally unique ID.

Recommended conceptual form:

```text
DeviceId + monotonic event sequence
```

or an equivalent UUID-based scheme.

The identity must not rely on the local SQLite row ID.

When two devices contain the same event because of retry/replay/import, the merge must recognize it as the same logical event.

---

# 27. Deterministic Ordering

Distributed clocks are imperfect.

The sync protocol should therefore distinguish:

```text
Event time
Logical mutation order
Receipt/upload time
```

Event timestamps are used for analytics.

Logical mutation versions are used for convergence.

The protocol must not infer chronology solely from upload time.

---

# 28. Concurrent Edits

Example:

```text
Device A: VS Code → Development
Device B: VS Code → Education
```

The system must not silently choose based solely on whichever device uploaded last.

Recommended V1 behavior:

- Preserve a conflict record.
- Apply deterministic base rule where safe.
- Surface the conflict to the user when it affects a user-maintained rule.
- Ensure the final rule can be reconstructed from history.

User classification history should therefore be modeled as versioned mutations rather than destructive overwrites.

---

# 29. Historical Corrections

When a user corrects a historical classification:

```text
User correction
   ↓
Local mutation
   ↓
Derived-data invalidation
   ↓
Sync mutation
```

A correction is not equivalent to adding a duplicate observation.

The sync format must carry enough information to reproduce the correction on another device.

---

# 30. Deletion Model

Deletion is harder than insertion because an old device may later reconnect with stale data.

Therefore deletion must create authenticated tombstones.

Conceptually:

```text
Delete object/range
      ↓
Create tombstone
      ↓
Replicate tombstone
      ↓
Peers learn deletion
      ↓
Stale object suppressed
```

The tombstone must survive for at least as long as a supported stale replica can reasonably reappear, subject to the recovery model defined by Document 10.

---

# 31. Range Deletion

A user may delete an entire date range.

A naive per-row tombstone model would be too large.

Use a logical range deletion representation where practical:

```text
Dataset: D
Time range: [T1, T2)
Data families: browser + titles + intervals
Deletion generation: G
```

The merge engine must evaluate object overlap against tombstone ranges.

Range deletion must not accidentally remove records outside the selected interval.

---

# 32. Delete-All History

A “delete all usage history” operation is special.

Preferred mechanism:

```text
Dataset deletion epoch / generation
      ↓
Delete current local history
      ↓
Publish authenticated dataset reset/tombstone
      ↓
Invalidate older remote objects
      ↓
Start fresh history generation
```

This prevents an old device from re-uploading an obsolete dataset without detecting the reset.

Exact key-epoch invalidation behavior is defined in Document 10.

---

# 33. Sync Disconnect

Disabling sync means:

```text
No new uploads
No new imports
No remote reconciliation
Local history remains intact
```

Pending upload state may remain locally until the user deletes/disconnects the dataset or chooses to discard the queue.

The UI should tell the user what happens to pending remote changes before permanently discarding them.

---

# 34. Re-Enabling Sync

When sync is re-enabled:

1. Re-authenticate as necessary.
2. Validate current dataset identity.
3. Fetch remote state.
4. Compare local sync checkpoint.
5. Reconcile remote and local changes.
6. Preserve local usage history unless a conflict/deletion rule explicitly determines otherwise.
7. Resume normal synchronization.

Re-enabling sync must not implicitly erase local history.

---

# 35. Device Migration

Device migration is a first-class workflow.

### Old device

```text
Device A
  ↓
continues local history
  ↓
uploads encrypted changes
```

### New device

```text
Device B
  ↓
sign in
  ↓
enable sync
  ↓
recover encrypted dataset
  ↓
import history
  ↓
continue recording
```

The logical history remains continuous while provenance records which device produced each observation.

The device switch itself should be represented as a lifecycle/provenance event rather than a fabricated usage gap.

---

# 36. Missing Device Scenario

A device can disappear without a clean shutdown.

Example:

```text
Device A last sync: Monday
Device A is lost
Device B starts Tuesday
```

Device B must continue from the last known dataset state without waiting for Device A.

If Device A later reconnects, its outstanding local mutations must be reconciled against the current dataset using the conflict/deletion rules.

---

# 37. Clock Skew

Different devices can have incorrect wall clocks.

The protocol must preserve:

- Original device wall-clock timestamp.
- Time-zone context where needed.
- Monotonic duration where available.
- Logical sync ordering.

A sync merge must not rewrite historical event timestamps merely to force chronological ordering across devices.

Analytics can later flag suspicious clock discontinuities.

---

# 38. Time Zone Handling

Stored canonical timestamps should remain in UTC according to Document 07.

The protocol may additionally preserve device/time-zone information needed to reproduce the user's local-calendar view.

When a device changes time zone, sync must not reinterpret existing events as though their UTC instants changed.

---

# 39. Retention and Remote Garbage Collection

Local retention and remote retention are related but not identical.

Example:

```text
Device A compacts old raw observations
Device B still has older raw observations
```

The sync system must not delete remotely retained data solely because one device compacted it locally unless the dataset-level policy says that such data is intentionally deleted.

A remote garbage collector may remove encrypted objects only when:

- They are no longer referenced by any supported manifest/version.
- Tombstone/recovery windows have elapsed.
- No enrolled device requires them.
- The operation is compatible with rollback/recovery guarantees.

The initial implementation may defer automated garbage collection and retain bounded historical ciphertext until the protocol is proven.

---

# 40. Schema and Protocol Versioning

Every sync object must identify:

```text
Protocol version
Schema version
Encryption format version
Algorithm version
```

Local software must reject unknown security-critical versions safely rather than guessing.

Backward compatibility should be explicit.

Example:

```text
Current reader supports:
protocol 1
schema 1–3
crypto 1–2
```

A future incompatible protocol requires an explicit migration path.

---

# 41. Crypto-Key Epochs

Sync objects reference a key epoch defined by Document 10.

Conceptually:

```text
Dataset
  ├── Key Epoch 1
  │      ├── objects
  │      └── manifest
  ├── Key Epoch 2
  │      ├── objects
  │      └── manifest
```

Rotation should allow authorized devices to transition from one epoch to another without requiring the complete dataset to be re-encrypted immediately.

A compromised/revoked device must not automatically receive future key epochs.

---

# 42. Integrity and Tamper Detection

Every remote object must be authenticated.

The client must verify:

- Envelope version.
- Dataset identity.
- Object identity.
- Key epoch.
- Authentication tag/MAC.
- Plaintext schema.
- Internal IDs.
- Time-range consistency.
- Referenced object integrity.

A failed verification must produce:

```text
Remote object rejected
Local state unchanged
Object quarantined/logged minimally
```

Do not automatically “repair” a cryptographically invalid object by trusting a second source of unverified metadata.

---

# 43. Rollback Protection

An attacker with access to the Drive contents might attempt to restore an older valid manifest.

The client should maintain local anti-rollback state, such as a protected highest-seen generation/epoch/checkpoint.

An older remote state must not silently replace newer local state.

Legitimate user recovery to an older dataset snapshot is a separate explicit operation.

---

# 44. Recovery Mode

When normal reconciliation encounters structural inconsistency:

```text
Normal sync
   ↓
validation failure
   ↓
quarantine
   ↓
Recovery mode
```

Recovery mode should preserve local history and give the user clear choices such as:

```text
Keep local history
Recover from remote snapshot
Export local data
Reset sync relationship
```

The application must not silently wipe local history to make sync “work again.”

---

# 45. Local Source-of-Truth Rule

Remote data is imported into local storage only through a controlled merge pipeline.

The local database remains authoritative for:

- Current analytics.
- Current classifications.
- Current timeline.
- Current local configuration.
- Current device tracking state.

The sync system provides additional replicated facts and mutations.

---

# 46. Tracker Isolation

The tracker runtime must not call Google Drive APIs.

The tracker communicates with the sync subsystem only through lightweight local contracts, for example:

```text
“new local data available”
“sync status changed”
“flush requested”
```

Heavy encryption, networking, Drive enumeration, and reconciliation occur outside the tracker.

This preserves the low resource target defined in Documents 05–07.

---

# 47. Sync Scheduling

Initial implementation target:

```text
Small local change:
queue quickly

Upload batching:
coalesce nearby changes

Periodic reconciliation:
approximately every 5–15 minutes while active

Manual sync:
user-triggered

Reconnect:
reconcile promptly after network/auth recovery
```

Exact cadence is a performance/product decision and must be benchmarked.

Sync scheduling should use adaptive backoff rather than frequent polling when idle.

---

# 48. Bandwidth Policy

Sync must be bandwidth-conscious.

Requirements:

- Batch small changes where practical.
- Avoid re-uploading unchanged objects.
- Use compression before encryption only when it improves size materially and is safe for the data shape.
- Never compress secrets in a way that creates an unintended cross-boundary oracle.
- Do not repeatedly redownload objects already verified locally.

Because encrypted data is not generally deduplicable by plaintext content at the provider, logical object identity must be managed by the client.

---

# 49. Network Failure Modes

### No network

```text
Tracking continues
Outbox grows within bounded limits
```

### DNS failure

```text
Backoff
No tight retry loop
```

### Drive service unavailable

```text
Backoff
Preserve local queue
```

### OAuth token expired

```text
Attempt safe token refresh
If unsuccessful → sync paused
```

### Permission revoked

```text
Sync paused
User-visible action required
```

None of these states should stop the tracker.

---

# 50. Queue Pressure

Long offline periods can create large queues.

The sync subsystem must have bounded resource behavior.

The implementation should:

- Persist queue metadata compactly.
- Avoid holding all pending payloads in RAM.
- Generate encrypted objects incrementally.
- Prioritize newer or user-requested changes when appropriate.
- Surface prolonged sync backlog.
- Never drop usage data silently.

If local storage is exhausted, that is a critical local data-health failure and must be surfaced separately from ordinary sync failure.

---

# 51. Data Freshness

The UI should distinguish:

```text
Synced
Syncing
Offline
Paused
Needs attention
```

A stale sync timestamp must never be presented as current synchronization.

Example:

```text
History synced 17 minutes ago
```

is preferred over a green checkmark that could imply stronger guarantees.

# 52. User-Facing Sync Status

The settings surface should expose:

- Sync enabled/disabled.
- Google account connected/not connected.
- Last successful sync.
- Pending data count/approximate backlog.
- Current error state.
- Device membership.
- Encryption status.
- Local-only mode.

Sensitive remote object identifiers should not be exposed unless useful for diagnostics.

---

# 53. Manual Controls

Recommended user controls:

```text
Sync now
Pause sync
Resume sync
Disconnect sync
Manage devices
Export encrypted backup
Reset sync relationship
```

“Reset sync relationship” must explain whether it:

- Keeps local history.
- Deletes remote state.
- Creates a new dataset identity.
- Requires re-enrollment.

---

# 54. Conflict UI

Most normal append-only synchronization should require no user intervention.

User intervention is appropriate for semantic conflicts such as:

```text
Category changed differently on two devices.
```

The UI should show:

```text
Current local rule
Other device change
When each change occurred
Which option will become canonical
```

The product should not expose cryptographic implementation details to ordinary users.

---

# 55. Security of Google Drive Access

The sync worker should use the narrowest practical Drive authorization scope.

It should avoid:

- Enumerating unrelated files.
- Reading arbitrary user documents.
- Modifying unrelated Drive content.
- Storing credentials in application data tables.

Drive object operations should be scoped to the application's own namespace.

The exact OAuth scopes must be validated against current Google API capabilities during implementation.

---

# 56. Drive Namespace Integrity

Remote object names/IDs must not be trusted merely because they exist inside the application folder.

The client must validate:

```text
object belongs to expected dataset
object type is recognized
protocol version is supported
object authentication succeeds
```

An object copied manually into the folder should not be able to poison the local dataset.

---

# 57. No Remote Execution

Downloaded sync data is data only.

The sync system must never execute:

- Code.
- Scripts.
- Plugins.
- Models.
- Arbitrary binaries.

Schema-driven deserialization should be used.

Unknown fields may be preserved only where explicitly safe and should not influence control flow.

---

# 58. Safe Deserialization

All remote data must pass:

```text
Size limits
Encoding validation
Schema validation
Range checks
String length limits
ID validation
Timestamp validation
Reference validation
```

before entering application objects.

The sync worker must assume remote inputs are malicious or corrupted even though the Drive account belongs to the user.

---

# 59. Sync Auditability

The local application should retain minimal sync-health history sufficient to answer:

```text
When did sync last succeed?
Why is sync paused?
How many retries occurred?
Was an object rejected?
When did a device join/leave?
```

This health metadata should not contain raw usage history.

---

# 60. Privacy Requirements

Sync must comply with Document 09.

Therefore:

- No behavioral telemetry.
- No third-party analytics in sync code.
- No raw usage data in network logs.
- No raw domains/titles in exception messages where avoidable.
- No diagnostic upload as a side effect of sync failure.
- Private data remains excluded.
- User deletion propagates.
- Local-only mode requires no Drive permissions.

---

# 61. Offline-First Correctness

A critical correctness test is:

```text
Day 1: offline
Day 2: offline
Day 3: online
```

Expected:

```text
All valid local history retained.
Sync queue reconciles.
No duplicate logical events.
No fabricated gaps.
No tracker interruption.
```

The same must hold for:

```text
Device A offline
Device B offline
Both later reconnect
```

---

# 62. Example Two-Device Merge

Initial:

```text
Dataset generation 10
```

Device A records:

```text
A1, A2
```

Device B records:

```text
B1, B2
```

A uploads first.

B uploads later from an older checkpoint.

Expected final logical dataset:

```text
A1
A2
B1
B2
```

not:

```text
B1
B2
```

and not duplicate copies of A1/A2.

---

# 63. Example Deletion Race

Device A deletes a time range.

Device B is offline and still has the old data.

Sequence:

```text
A creates tombstone T
A syncs T
B later reconnects with old event E
```

Expected:

```text
T dominates E.
E is not resurrected.
```

This is a mandatory integration test.

---

# 64. Example Reset Race

Device A performs “delete all history.”

Device B was offline before the reset.

After reconnection, B must learn that the prior dataset generation is obsolete.

The implementation must not allow B to repopulate the deleted history automatically.

This should be enforced through generation/reset metadata and cryptographic epoch changes where appropriate.

# 65. Initial Sync

Initial sync can involve substantial data.

Recommended sequence:

```text
Create local checkpoint
↓
Fetch remote manifest
↓
Validate remote state
↓
Download required historical shards
↓
Stage
↓
Merge
↓
Build/rebuild derived aggregates
↓
Set checkpoint
↓
Upload local deltas
```

Tracking continues throughout.

Analytics can temporarily expose:

```text
History import in progress
```

rather than blocking the entire UI.

---

# 66. Initial Import and Large History

The application should avoid loading years of history into RAM.

Use streaming/batched import:

```text
Download shard
→ decrypt
→ validate
→ batch insert/merge
→ release memory
→ next shard
```

Database transactions should use bounded batches.

---

# 67. Derived Analytics Synchronization

Derived aggregates generally should not be treated as the sole synced source of truth.

Preferred model:

```text
Sync durable observations + user mutations
        ↓
Local rebuildable aggregates
```

Precomputed aggregates MAY be synchronized as optimization/cache objects, but correctness must remain reconstructable from authoritative data.

---

# 68. Classification Synchronization

User-defined classification rules are semantic state and therefore must be synchronized.

A rule should include a stable rule ID and version metadata.

Example:

```text
Rule R1
Pattern: executable=Code.exe
Category: Development
Priority: 100
Updated by: Device B
Version: 42
```

Rules must remain distinguishable from raw observed identity.

# 69. Privacy Setting Synchronization

Privacy controls require special treatment.

Some settings are device-local by design, while others may be account/dataset-wide.

Default categories:

```text
Tracking runtime health → device-local
Local database path → device-local
Window title collection → potentially user preference
Page title collection → potentially user preference
Sync enabled → account/device relationship
Retention policy → explicit dataset policy where intended
```

The product must not unexpectedly propagate a local device privacy preference to every device.

Any synchronized privacy setting requires an explicit scope label:

```text
device
user
 dataset
```

---

# 70. Sync of User Deletions vs. Retention

A retention compaction is not necessarily a user deletion.

The protocol must distinguish:

```text
Compaction:
“Local representation no longer needs this raw layer.”

Deletion:
“The user intentionally wants this information removed.”
```

Only the latter should necessarily generate user-data deletion tombstones, subject to the dataset policy.

---

# 71. Export/Import Relationship

Encrypted sync packages should be usable as the basis for migration/recovery where practical.

However:

```text
Sync object format
```

and

```text
human-readable export format
```

are separate concerns.

Human-readable CSV/JSON exports should never be uploaded to Drive automatically as a substitute for encrypted sync objects.

---

# 72. Sync and Automatic Updates

A software update may introduce a new sync protocol.

Update sequencing must ensure:

```text
Old client
→ remains able to read supported prior objects

New client
→ upgrades protocol safely
```

An update must not strand the user's only copy of history.

Before a destructive migration, the client should preserve or verify a recoverable local state.

---

# 73. Protocol Migration

Protocol changes should follow:

```text
Detect old version
↓
Verify supported migration
↓
Create safety checkpoint
↓
Migrate local representation
↓
Publish new encrypted objects
↓
Retain compatibility window
↓
Garbage-collect only after safety criteria
```

Migration code must be replayable/testable on fixture datasets.

---

# 74. Performance Targets

Sync must be isolated from the tracker and remain lightweight in ordinary operation.

Suggested starting targets:

- Tracker CPU impact: unchanged from tracker budget while sync is active.
- Typical sync-worker CPU: <2% sustained on a modern laptop during steady-state sync.
- Typical sync-worker RAM: <150 MB; target substantially lower for steady state.
- No continuous polling loop when idle.
- Bounded concurrent Drive requests.
- Bounded encryption/decryption batch size.
- Initial-history import should yield periodically rather than monopolize disk/CPU.

These are engineering budgets, not guarantees; benchmark on representative Windows hardware.

# 75. Failure Isolation

### Tracker crash

Sync continues to operate only on safely committed data and later reconciles.

### Sync crash

Tracker continues.

Pending outbox state remains durable.

### UI crash

Sync worker may continue if independently hosted.

### Drive outage

Local tracking unaffected.

### Authentication failure

Local tracking unaffected.

### Remote corruption

Local source of truth unaffected.

# 78. Security Test Matrix

The sync test suite must include:

### Crypto

- Tampered ciphertext rejected.
- Wrong key rejected.
- Wrong dataset ID rejected.
- Wrong key epoch rejected.
- Modified authenticated metadata rejected.

### Consistency

- Duplicate upload deduplicates.
- Replay converges.
- Old manifest cannot overwrite newer checkpoint.
- Missing object is detected.
- Broken object reference is quarantined.

### Privacy

- Private browser fields never appear in sync payloads.
- Diagnostics do not leak usage data.
- Logs do not contain raw domains/titles.

### Failure

- Process kill during upload.
- Process kill after remote commit but before local acknowledgement.
- Network loss during download.
- OAuth expiry during reconciliation.
- Drive permission revocation.

### Deletion

- Range deletion converges.
- Delete-all reset converges.
- Offline stale device cannot resurrect data.

# 79. Property-Based / Model Testing

The merge engine is suitable for state-machine/property testing.

Important properties:

```text
Merge(Merge(A, B), C) == Merge(A, Merge(B, C))
```

where equivalence is defined over the logical dataset state.

Also test:

```text
Merge(A, A) == A
```

and, where applicable,

```text
Merge(A, B) == Merge(B, A)
```

For mutation streams, exact commutativity may not always hold; define ordering semantics explicitly rather than forcing an invalid algebraic property.

# 84. Remote Dataset Deletion

A separate operation should allow the user to remove the synchronized dataset from Drive.

Recommended confirmation should state:

```text

```

After remote deletion, the client should create a new logical dataset/reset state so stale clients do not silently repopulate deleted data.

# 85. Account Change

Switching Google accounts must not silently merge histories.

Sequence:

```text

  ↓
Disconnect
  ↓

  ↓
Connect new account
  ↓

  - new dataset
  - recover existing dataset if authorized
```

Account identity changes are security-sensitive.

# 86. Multiple Local Windows Users

The initial product should treat a Windows user profile as the local data boundary.

Do not merge usage histories of separate Windows users merely because they share a physical machine.

If multi-user/shared-PC support is introduced later, it requires an explicit identity model.

---

# 87. Shared Computer Privacy

The local history database should be associated with the intended Windows user account and protected using the local security mechanisms from Document 10.

A different Windows user should not automatically be able to read another user's history merely by opening the data directory.

---

# 88. Data Corruption Recovery

If SQLite is healthy but remote sync metadata is corrupt:

```text
Preserve SQLite
Reset sync metadata
Reconcile from local state
```

If SQLite itself is corrupt:

```text
Stop destructive operations
Preserve database file
Attempt supported recovery/export
Rebuild from validated backups if available
```

Sync must never use a remote copy to silently overwrite potentially recoverable local data.

---

# 89. Backup Relationship

Encrypted sync is not necessarily a complete backup solution.

The UI should distinguish:

```text
Sync
“Keep devices converged.”

Backup
“Keep a recoverable copy.”
```

The same encrypted object system may eventually support both, but the user-facing semantics remain distinct.

# 95. Acceptance Criteria

## Functional

- Two devices converge on append-only history.
- Duplicate retries do not duplicate logical events.
- User corrections converge.
- Deletions converge.
- Delete-all reset converges.
- Device migration preserves logical history.
- Offline tracking continues.

## Security

- Drive contains ciphertext only for usage content.
- Tampering is detected.
- Old remote state cannot silently roll back local state.
- Revoked devices cannot publish future authorized state.
- OAuth credentials are separated from usage data encryption keys.

## Privacy

- No behavioral telemetry.
- Private browser data never enters sync objects.
- Logs do not expose domains/titles.
- Sync is opt-in.
- Sign-in alone does not upload history.

## Reliability

- Process termination during upload is recoverable.
- Network loss is recoverable.
- Auth expiration does not affect tracking.
- Remote corruption does not damage local source of truth.

## Performance

- Sync does not materially increase tracker CPU wakeups.
- Queue memory remains bounded.
- Large history imports are incremental.
- Idle sync has no tight polling loop.

# 96. Hard Invariants

1. Local SQLite is authoritative.
2. Drive is never authoritative.
3. Tracker never waits on Drive.
4. Tracker never requires network connectivity.
5. Sync is explicitly enabled.
6. Google sign-in does not equal sync consent.
7. Plaintext usage history never enters Drive.
8. Private/incognito usage detail never enters sync.
9. OAuth credentials never enter the usage dataset.
10. Immutable encrypted objects are preferred over in-place mutation.
11. Every logical mutation has stable identity.
12. Remote objects are authenticated before import.
13. Stale remote state cannot silently roll back newer local state.
14. Tombstones prevent deletion resurrection.
15. Dataset reset prevents old devices from repopulating deleted history.
16. User history deletion is distinguishable from local compaction.
17. Sync failures never stop tracking.
18. Remote corruption never destroys local source-of-truth data.
19. New sync protocol versions are explicit and validated.
20. Sync diagnostics do not become behavioral telemetry.

# 97. Definition of Done for Document 11

Document 11 is implemented when:

- Local sync metadata and outbox are durable.
- Encrypted object envelopes are versioned and authenticated.
- A deterministic local merge engine passes replay/property tests.
- Two or more devices converge correctly under concurrent append/edit/delete scenarios.
- Range deletion and full-history reset cannot be undone by stale devices.
- Google Drive integration is isolated behind a remote-store abstraction.
- OAuth credentials are protected and independent from data encryption keys.
- Initial import is incremental and does not block tracking.
- Offline/reconnect behavior is reliable.
- Sync status is visible and honest.
- Remote corruption and rollback are detected.
- Privacy invariants are enforced in the ingestion/sync layer, not only the UI.
- Device migration works without creating a second logical history.
- Automated tests cover process termination, network failure, auth failure, concurrent devices, deletion races, and protocol migration.
